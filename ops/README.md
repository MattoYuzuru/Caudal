# Эксплуатация Caudal

Control plane слушает `127.0.0.1:18260`. На HTTPS-домен выводится отдельным [сайтом Caddy](caudal.caddy). Существующие маршруты, SSH и служебные порты сохраняют свою конфигурацию.

## Установка

1. Возьмите архив для конкретной успешной ревизии из GitHub Actions или соберите его с `scripts/package.sh "$(git rev-parse HEAD)" build` после сборки веба. Сверьте архив по соседнему файлу `.sha256` и извлеките в закрытый staging-каталог. При переносе из внешнего источника отдельно проверьте происхождение сборки.
2. Создайте `/etc/caudal` с правами `0700`. Поместите в него разные случайные секреты `owner-password` и `mcp-token` с правами `0600` и доступом root. Сохраните закрытую копию у владельца. В `control.env` задайте `CAUDAL_ORIGIN=https://vps.keykomi.com` и `CAUDAL_LISTEN=127.0.0.1:18260`.
3. Установите `caudal.service` в `/etc/systemd/system`, затем выполните `systemctl daemon-reload`. Запустите `sudo ops/install-release.sh /private/staging/caudal-REVISION`. Установщик проверяет контрольные суммы, переключает `current` и сверяет версию в `/healthz`. После успешного запуска включите `caudal.service` при загрузке.
4. Добавьте фрагмент сайта в существующую конфигурацию Caddy. Выполните `caddy validate --config /etc/caddy/Caddyfile` перед reload. После reload проверьте внешний TLS, `/healthz`, страницу входа и ответ `401` при анонимном запросе `/api/v1/fleet`.
5. Войдите с учётными данными владельца и пройдите регистрацию ноды. Проверьте историю после первого heartbeat и чтение через отдельный MCP-токен.

Для продакшна без серверного ключа владельцы вводят свой DeepSeek API key в консоли. Для отдельного серверного ключа сервис поддерживает `DEEPSEEK_API_KEY_FILE`. Храните его в отдельном системном credential и передайте сервису через override. Владельцы control plane управляют процессом, через который проходит запрос к DeepSeek.

В `control.env` можно задать `CAUDAL_CONTROL_PLANE_NODE_ID` как ID ноды, на которой действительно размещён Caudal. Это позволяет в разделе «Маршруты» связать свежий heartbeat другой ноды с подтверждённым HTTPS-маршрутом до хоста Caudal. Для авторизованных прокси Teleport используйте `CAUDAL_TELEPORT_PROFILES` по [описанию интеграции](../docs/teleport.md). Проверка прокси выполняется из сети control plane.

## Сборщик на конкретном узле

- Положите соответствующий бинарник в `/usr/local/bin/caudal-agent` с правами `0755`. Установите `caudal-agent.service` в `/etc/systemd/system`.
- В `/etc/caudal/agent.env` задайте `CAUDAL_URL` с HTTPS origin. Сохраните выданный только этому узлу токен в `/etc/caudal/agent.token` с правами `0600`. Система передаст токен непривилегированному процессу через `LoadCredential`.
- Выполните `systemctl daemon-reload` и `systemctl enable --now caudal-agent`. Сверьте первую точку в консоли. При отзыве замените секрет на узле и перезапустите сборщик.
- `systemctl show caudal-agent -p MemoryCurrent -p MemoryPeak -p CPUUsageNSec` показывает память cgroup и накопленное CPU-время. Снимите два значения CPU с известным интервалом. Логи сборщика доступны через `journalctl -u caudal-agent`.

## Откат и данные

Новое развёртывание сохраняет предыдущий каталог под `/opt/caudal/releases`. При провале локальной проверки установщик переключает ссылку обратно и перезапускает unit. Если проверка внешнего HTTPS не проходит после первого развёртывания, отключите добавленный фрагмент Caddy, проверьте конфигурацию и сделайте reload. Данные и секреты можно сохранить для диагностики.

Состояние хранится под `/var/lib/caudal`. Резервируйте этот каталог в закрытое хранилище, отдельно от бинарников и credential-файлов. Веб-сессии находятся в памяти и прекращаются после перезапуска. Формат записи один на ноду, с хэшем токена и ограниченной историей. Один экземпляр control plane владеет каталогом данных.
